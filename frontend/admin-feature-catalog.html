Operations and constraints

Projects

  • Filterable, paginated global list and detail.
  • Create and edit in a drawer; create requires an active owner.
  • Transfer owner explicitly: old owner becomes a member, new owner is removed from memberships.
  • Add/remove memberships only for eligible active users; owner and duplicate selections are excluded.
  • Delete requires a confirmation. A cascade_confirmation_required conflict reveals task and member counts and requires a second confirmation.

Tasks

  • Filter by project, search, status, priority, and due state; paginate through URL query state.
  • Create/edit in a drawer; existing project, active-assignee, dependency, completion, and cycle validation remains authoritative.
  • Expose permitted subtask CRUD, dependency add/remove, comment inspection/deletion, and read-only activity.
  • Every destructive task or nested operation opens the shared confirmation dialog.

Notifications and preferences

  • Filter global notifications by user, type, and unread state.
  • Delete only after confirmation; no mark-read, resend, or content rewrite controls.
  • Load a user preference record and update only delivery booleans and reminder days when permitted.

Reports

  • Workspace task CSV and project CSV use safe browser download handling.
  • AI project report is a backend-generated CSV with server report limits.
  • Filename is sanitized client-side; errors do not create a download.

Audit

  • Filter by action, resource, actor, target, outcome, ID, and time range.
  • Rows and a detail panel are read-only.
  • Deleted actors are rendered as the neutral backend label “Deleted user”.

System

  • Shows only email_configured and ai_configured.
  • No credential inputs, secret values, provider probes, or configuration mutation.

Lifecycle flows

  1. Authenticate: existing token interceptor attaches JWT; admin capability lookup gates the shell.
  2. Discover: navigation and action controls derive from exact effective permissions.
  3. Load: each module shows a status spinner, preserves URL filters where applicable, and guards stale responses.
  4. Edit: entity edits use a right-side drawer with focus trap, Escape close, and focus return.
  5. Mutate: request errors preserve form or confirmation context; stable conflict codes are shown with actionable impact.
  6. Confirm destruction: destructive actions require an accessible confirmation before network mutation. Project cascade requires a second impact confirmation.
  7. Recover: success status is visible in-page; retry controls reload failed reads; empty and no-match states explain next steps.
  8. Download: report response becomes a sanitized local browser download only after a successful response.
Conflict behaviorStable codes such as cascade_confirmation_required, project_name_in_use, active_owner_required, active_member_required, and backend validation messages are never replaced by a generic success toast.

Accessibility and responsive expectations

  • Semantic landmarks, headings, labels, lists, tables, forms, buttons, and dialogs are used for their meaning.
  • Every icon-only control has an accessible label; important async feedback uses role="status" or role="alert".
  • Every enabled button has a pointer cursor and visible :focus-visible treatment; disabled controls communicate why they cannot run.
  • Drawers and confirmation dialogs trap focus, close on Escape when not busy, and return focus to the trigger.
  • Desktop layouts use split list/detail compositions; narrow layouts stack content without removing required actions. Touch targets are at least approximately 44px high.
  • Long titles, descriptions, comments, metadata, IDs, and filenames wrap or scroll without page-wide overflow.
  • Color is paired with text labels; reduced motion is respected by the existing utility-based styling.

Security and data invariants

Backend is authoritativeFrontend permission hiding is usability and information minimization, not authorization. Every API request is protected by backend permission dependencies.
No secret exposureHealth screens render booleans only. Catalog has no API calls or credentials. Report content and filenames are server-controlled and sanitized.
Data integrityAdmin access does not bypass active-user, same-project, dependency-cycle, completion, or project-name invariants.
Moderation boundaryComments can be inspected/deleted if permitted; authorship is never rewritten. Activity and audit are read-only.
Deletion impactNo bulk destructive controls. Project and task deletion explain nested impact before confirmation; audit metadata contains counts, not content.
Deleted identitiesDeleted audit actors render neutrally and the interface does not reconstruct deleted identity details.

Migration notes

  • Frontend consumes the Task 5–7 admin routes and does not change backend schemas, permissions, or conflict codes.
  • Existing deployments must include the Task 5–7 backend routes before these modules are usable; older servers will show module errors rather than silently falling back to ordinary workspace APIs.
  • The catalog is an internal review artifact at frontend/admin-feature-catalog.html; Vite does not copy it into dist.
  • No npm dependency or database migration is required by this frontend task.

Non-goals

  • No bulk destructive actions.
  • No ordinary workspace membership or project workflow redesign.
  • No notification mark-read, content editing, resend, or moderation rewrite.
  • No audit mutation, system credential editing, provider probing, or secret display.
  • No new auth model, state library, API client, or component library.

Reviewer checklist

  • Confirm exact permission hiding for navigation and direct denied URLs.
  • Verify project creation and owner transfer cannot choose inactive users.
  • Verify membership add excludes owner, duplicates, disabled users, and deleted users.
  • Verify project cascade conflict displays backend counts and requires explicit second confirmation.
  • Verify task nested permissions independently hide subtask, dependency, comment, and activity controls.
  • Verify every delete path opens confirmation before the request.
  • Verify no comment update or activity mutation exists in the UI or API builder.
  • Verify notifications do not mark read or rewrite content.
  • Verify CSV downloads succeed safely and failed blobs do not create files.
  • Verify audit is read-only and deleted actors are neutral.
  • Verify system only renders two booleans and contains no credential fields.
  • Run node test, lint, build, and diff check; verify the catalog is absent from dist.
  • Check authenticated routes at 1280px and 390px with keyboard focus and a screen reader pass.
